# Registration, activation and verified initial training

## Confirmed scope and pending decisions

The requested technical path is implemented: API-verified Jotform registration creates a persisted invited account, mailbox verification activates it, new dealers have restricted access, and a trusted recorded initial-training completion unlocks dealer features. Class selection, enrollment, todo completion, certification labels, Jotform workflow labels and dealer numbers never grant this access.

The repository does not establish the approved source of initial-training completion, the responsible verifier, a Jotform assignment manager, grandfathering rules, agreement prerequisites, dealer-number issuance or CRM mapping. No training curriculum or financing terms are inferred. Deployment must obtain these decisions. The implementation exposes these explicitly proposed policies:

- New dealers can use setup/home, training selection/history, support/chat, and account/security/privacy controls. Benefits, financing, resources, equipment, marketing, warranty and rebates require verified initial training.
- Pre-existing accounts retain existing access (`EXISTING_ACCESS`) pending an approved roster migration. This is not a claim that they completed training or a finalized grandfathering rule. New invitation-created dealers are restricted too.
- A configured verifier can record initial training only for their assigned active dealers, with the approved source, evidence reference and completion time. Configuration is an explicit administrative approval, not an inferred role grant. Ordinary managers have no completion-write permission by default.
- This step unlocks application features only. It does not mark full certification, issue LG Pro Dealer numbers or assert signed agreements.

## Deployment configuration

Apply `20261020000000_verified_onboarding` and `20261020020000_restrict_new_accounts`, then generate Prisma. The second migration changes the default for future users to restricted while leaving existing rows untouched. All relevant environment variables are documented in `.env.example`:

- `JOTFORM_ONBOARDING_ENABLED=true` explicitly enables account provisioning after canonical API verification. It does not change webhook security, reconciliation, queue leases or retry policy.
- `JOTFORM_ONBOARDING_MANAGER_ID` must identify the business-approved active sales manager. Missing or invalid assignment leaves the imported submission in review (`ONBOARDING_MANAGER_REQUIRED`) without guessing an owner. Configure it and replay selected submissions using the existing replay command.
- `ONBOARDING_VERIFIER_MANAGER_IDS` lists explicitly approved manager user IDs, comma-separated. Blank disables completion writes. Owners must check the agreed training evidence before submitting a verification.
- Existing SMTP settings and `JWT_SECRET` are required for activation delivery. The security-email worker handles encrypted durable outbox delivery/retries. A dealer can request a new code from the activation screen when the initial 15-minute code expires. No real mail is sent by the automated tests.

Do not enable production provisioning before the assignment, restricted feature matrix, data processing and verification owner/source are approved. A controlled deployment test must validate real mail with an authorized test recipient and actual Jotform credentials; those external systems were not contacted during local implementation.

## Registration-copy recipients

The requested recipient list is reserved as blank `JOTFORM_REGISTRATION_NOTIFICATION_EMAILS` in `.env.example`. Add business-approved email addresses later as a comma-separated list. No addresses have been invented, no new registration-copy sender has been added, and this placeholder does not deliver email. Approved recipients and delivery routing must be supplied before a delivery integration is implemented and tested; existing Jotform/Zapier recipients and routing continue unchanged.

This recipient list is separate from `JOTFORM_ONBOARDING_MANAGER_ID` (account ownership) and `ONBOARDING_VERIFIER_MANAGER_IDS` (trusted training-update authorization). Adding an email to the recipient list does not grant either permission or settle the pending onboarding policies.

## Contract

- `POST /auth/activation/request` accepts `{email}` and returns the same message for missing, active, disabled and pending accounts.
- `POST /auth/activation/confirm` accepts `{email, code, password, firstName, lastName, termsAccepted: true}`. The eight-digit code expires after 15 minutes, has five failed attempts, is single-use and purpose/session-bound. Password rules match recovery (12–72 characters and no more than 72 UTF-8 bytes). Activation verifies the exact originally persisted registration, binds ownership after mailbox proof, writes legal acceptance and credentials, consumes all challenges and invalidates previous sessions. The client signs in normally afterwards.
- `/auth/login`, `/auth/refresh`, `/auth/me`, `/me` and profile/legal updates return `user.onboarding`: `{state, restricted, trainingVerifiedAt, nextAction, allowedFeatures}`. `/me/onboarding-status` adds the same contract as `access`. This response is independent of legacy summary counters.
- `GET /onboarding/prospects/:id` returns `{access, verification, canVerifyTraining}` to the assigned manager only.
- `POST /onboarding/prospects/:id/training-verification` accepts `{completedAt, source, reference, enrollmentId?}`. Dates must be past ISO timestamps. An optional enrollment must belong to the same dealer, be uncanceled and have ended by completion. Exact retries return the original audit record; changed evidence conflicts. Writes are transactional and serialized by account lock. The record captures verifier, source, reference, completedAt and verifiedAt; deleting a manager removes the verifier relation without breaking account deletion. Deleting the dealer cascades the verification record.

## Security and ownership boundaries

Protected HTTP endpoints deny restricted accounts by default in `JwtAuthGuard`; only explicit `AllowBeforeTraining` controllers bypass the training gate. Role checks and existing manager/participant ownership checks still apply. Every request reloads the access facts from the database, so existing bearer tokens unlock after a successful verified completion and cannot self-assert status. The messaging socket remains an allowed support feature with its existing authentication and participant checks.

Jotform provisioning runs in the existing verified canonical-write transaction and privacy lock. Duplicate canonical processing creates no second account or activation message. Existing accounts matched by email are never modified or linked. The original source submission is uniquely associated with a newly created pending account; subsequent source email edits require identity review and cannot create a second account. Imported names/raw answers remain unpersisted; the mailbox-verified applicant supplies their name at activation. Disabled accounts, erasure tombstones and deletion review remain protected. Original Jotform/Zapier recipient routing is untouched.

## Temporary local training toggle

For development-only walkthroughs, `PATCH /onboarding/development/training` accepts `{ "completed": true }` or `{ "completed": false }` for the authenticated active dealer. No target-user ID is accepted. Both `DEV_FEATURES_ENABLED=true` and `DEV_TRAINING_TOGGLE_ENABLED=true` are required. Local development uses `NODE_ENV=development` or `test`, optional `APP_ENV=development`, and a PostgreSQL URL whose host is `127.0.0.1`, `localhost` or `::1` and database name ends in `_dev` or `_test`; host overrides are rejected. Hosted testing uses explicit `APP_ENV=preview` on the isolated test backend and keeps `NODE_ENV=production`. Hosted preview training writes are limited to reserved synthetic `hercules.local` dealer identities; real dealer accounts receive 404. Existing genuine verification evidence remains protected. `APP_ENV=production` or an unknown deployment always denies development tools, as does an absent `APP_ENV` with a production/missing/unknown `NODE_ENV`.

`DEV_FEATURES_ENABLED` defaults to disabled. It also gates synthetic `hercules.local` account login and existing HTTP/Socket.IO sessions, known demo invitations, legacy raw invite lookups, recipientless registration invitations, Swagger and demo seeding. Swagger additionally requires `ENABLE_SWAGGER=true`. Broad demo seeding additionally requires `ALLOW_DEMO_SEED=true` and a loopback PostgreSQL database named `*_dev`, `*_test` or the established local `faith_project`; it cannot run against a hosted preview database. The frontend independently requires its permitted development/preview app environment, `EXPO_PUBLIC_DEV_FEATURES_ENABLED=true` and `EXPO_PUBLIC_DEV_TRAINING_TOGGLE=true`. Keep the master and feature flags false in production.

To prepare login fixtures on the isolated hosted preview after migrations are deployed, run `ALLOW_PREVIEW_FIXTURES=true npm run preview:fixtures` with the host already configured as `APP_ENV=preview` and `DEV_FEATURES_ENABLED=true`. This idempotent command prepares only `manager@hercules.local` and `prospect@hercules.local`, their profiles, dealer onboarding tasks and shared support conversation. It uses the existing demo-login password, starts the demo dealer restricted, preserves development training state, and refuses any reserved identity with a conflicting role, imported activation link or genuine training evidence. It does not seed public content, reassign real dealers, issue invitations or send messages. Supply `ALLOW_PREVIEW_FIXTURES` only to this command; keep it false/unset in persistent host configuration. Existing synthetic accounts with a replaced password have their old sessions invalidated.

Hosted preview retains production authentication and transport requirements: a non-default `JWT_SECRET` of at least 32 characters and HTTPS `CORS_ORIGIN`. Explicit `APP_ENV=preview` may omit `MESSAGE_BLOCKED_TERMS` and `OPERATIONS_WEBHOOK_URL` until Hercules supplies the real business policy and operations destination. With no webhook, preview workflows requiring operations review return a clear 503 before committing changes; automatic dealer deletion may still complete. A configured preview webhook must use HTTPS. True production continues to require both moderation terms and the operations webhook. The Procfile runs database migrations before starting the web process. Do not change `NODE_ENV` to bypass these checks.

Apply `20261020030000_development_training_marker` before using it. This adds an explicit `developmentOnly` marker to distinguish synthetic training evidence from genuine verification. Toggling on creates one marked audit record and sets the existing training timestamp; toggling off deletes only that marked record and clears its timestamp. The same session's API permissions, authentication response and onboarding summary update on the next request. Enrollment, certification, account ownership, notification preferences and credentials stay unchanged.

Use a new restricted synthetic dealer. Genuine manager records (including records whose manager was later deleted), unexplained existing verification timestamps and legacy existing-access accounts return 409 and remain unchanged. Turn off the mock before recording a real manager verification. Disabling the environment flag hides/blocks the tool; it does not erase local fixture data. No production database or real external training record is modified by this tool.
